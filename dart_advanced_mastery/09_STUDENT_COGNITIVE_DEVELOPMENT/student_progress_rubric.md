# Comprehensive Student Progress & Competency Tracking Rubric
## مصفوفة تقييم ومتابعة التطور المعرفي والهندسي للطالب

> **الفلسفة التقييمية:**  
> نحن لا نقيس جودة الطالب بدرجة الامتحان النظري فقط؛ فالامتحان يقيس الحفظ المؤقت. هذا النظام يقيس **الكفاءة الهندسية الشاملة (Holistic Engineering Competency)** عبر 8 أبعاد محورية، بمقياس من 1 إلى 5، مع وضع خطط تدخل فوري لكل طالب يقل مستواه عن المعيار المطلوب.

| **1. الفهم المفاهيمي (Conceptual)** | خلط بين `var` و`dynamic`، عدم إدراك عمل الـ Event Loop، واستخدام عشوائي للكلمات المفتاحية. | فهم جيد للمفاهيم الأساسية، يحتاج لمساعدة في التفاصيل الدقيقة كـ Mixin Linearization. | استيعاب عميق للـ Type System، معمارية الـ Dart VM، والتمثيل الفيزيائي في الذاكرة. |
| **2. الدقة وصحة الكود (Accuracy)** | كود مليء بالأخطاء المنطقية والـ Null Exceptions ولا يمرر الـ Analyzer بسهولة. | كود يعمل في الحالات الطبيعية (Happy Path) لكن يتعثر في الـ Edge Cases النادرة. | كود محصن رياضياً (Defensive Code)، يمرر جميع الـ Unit Tests ولا يعاني من أي Memory Leak. |
| **3. حل المشكلات (Problem Solving)** | عجز عن تفكيك المسألة، ويبدأ بالنسخ واللصق دون منهجية واضحة. | يفكك المشكلة لمعظم عناصرها، ويصل للحل بعد عدة محاولات وتجربة يدوية. | يتبع منهجية ستانفورد الـ 12 بصرامة، ويحل المسائل بـ $O(N)$ أو $O(\log N)$ ببراعة. |
| **4. التفكير التحليلي (Analytical)** | لا يستطيع حساب الـ Big O، ولا يدرك الفارق في السرعة بين $O(N)$ و $O(N^2)$. | يحسب الـ Time Complexity بشكل صحيح، ويقارن بين الخوارزميات الشائعة. | يحلل الـ Time & Space بدقة رياضية صارمة، ويقيس الـ Heap Allocations بالـ DevTools. |
| **5. مهارة التصحيح (Debugging)** | ارتباك عند ظهور الـ Exception وتغيير الكود عشوائياً حتى يختفي الخطأ بالصدفة! | يقرأ الـ Stack Trace ويصل للسطر المسبب للخطأ ويصلحه خلال دقائق. | يستخدم الـ Breakpoints، يفحص الـ Memory Dumps، ويصل للسبب الجذري (Root Cause) بثقة. |
| **6. جودة الكود ونظافته (Clean Code)** | كلاسات ضخمة، دوال من 100 سطر، وتسميات مبهمة للمتغيرات مثل `a`, `temp2`. | كود منظم يلتزم بمعايير Effective Dart مع تطبيق جزئي لمبادئ SOLID. | تصميم معماري أنيق، أسماء معبرة، التزام كامل بـ SOLID و Sealed Types و Immutability. |
| **7. التواصل وشرح الكود (Communication)** | عجز عن شرح فكرة الكود، دفاع هجومي متوتر عند توجيه أي نقد. | شرح جيد للوظيفة العامة للكود، واستجابة هادئة لملاحظات الزملاء. | أسلوب مهني راقٍ في الـ PR Review، وشرح واثق يربط الكود بأهداف الـ Business. |
| **8. اتخاذ القرار الهندسي (Decisions)** | يختار الأدوات عشوائياً، ولا يعرف لماذا استخدم كلاس بدلاً من ميكسن. | يبرر اختياراته بالسرعة أو البساطة، ويدرك بعض التكاليف الجانبية. | وعي معماري كامل بالـ Trade-offs؛ يوازن بدقة بين السرعة والذاكرة وقابلية الصيانة. |

## 3. خطط التدخل والتطوير (Intervention & Acceleration Protocols)

### أ. بروتوكول الإنقاذ للطلاب المتعثرين (Remediation Protocol)
إذا حصل الطالب على أقل من 24/40 (أو أقل من 3 في بعدي حل المشكلات والتفكير المفاهيمي):
1. **جلسة تفكيك فردية (1-on-1 Office Hour):** 30 دقيقة تركز على حل مسألة واحدة بسيطة خطوة بخطوة بالورقة والقلم.
2. **سحب المساعدة التدريجي (Faded Scaffolding):** إعطاء الطالب مسألة مع كود شبه جاهز ينقصه سطران فقط، ثم زيادة النقص تدريجياً.
3. **منع استخدام الـ IDE مؤقتاً:** إجبار الطالب على كتابة الكود على ورق أو سبورة بيضاء لمنع التخمين العشوائي.

### ب. مسار التسريع للطلاب المتفوقين (Acceleration & Honors Track)
إذا حصل الطالب على أكثر من 36/40:
1. **تحديات خوارزمية متقدمة (Hard LeetCode / Codeforces):** تكليف الطالب بمسائل تتطلب Dynamic Programming أو Graph Algorithms في Dart.
2. **تحليل الـ Dart SDK Source Code:** قراءة كود الـ `List` أو `Stream` المكتوب بلغة Dart داخل الـ GitHub Repository الرسمي.
3. **تكليفه بدور Senior Code Reviewer:** مراجعة كود زملائه وتقديم ملاحظات معمارية نقدية.
