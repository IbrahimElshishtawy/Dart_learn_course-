# Live Coding Teaching Methodology & Think-Aloud Protocol
## دليل ومنهجية الشرح بالبرمجة الحية وبروتوكول التفكير بصوت مسموع

> **الهدف الهندسي:**  
> إزالة الرهبة من كتابة الكود عند الطالب، وإظهار أن المهندس المحترف لا يولد وفي رأسه الكود النهائي الكامل؛ بل يبدأ بتحليل المشكلة، ويكتب حلاً أولياً، ويتعرض لأخطاء يحللها بهدوء، ثم يعيد هيكلة الكود (Refactoring) للوصول إلى التصميم الهندسي الرصين.

## 2. تفصيل الخطوات السبع وسيناريو المحاضر باللهجة المصرية

### الخطوة 1: تحديد المشكلة وحدودها (Problem Definition)
- **فعل المحاضر:** يفتح ملف Dart فارغاً بالكامل ويكتب تعليقاً في الأعلى يوضح المدخلات، المخرجات، والقيود.
- **ماذا يقول المحاضر؟**
  > *"دلوقتي يا شباب، مطلوب مننا نعمل محرك تحقق من رصيد محفظة إلكترونية `WalletBalanceManager`. العميل هيدخل قيمة المعاملة، والمحرك لازم يتأكد إن الرصيد يكفي، ومفيش قيم سالبة، وكل ده يتم في كود سريع وآمن ضد الـ Null وما يعملش Memory Leak. جاهزين نبدأ؟"*

### الخطوة 2: التفكير بصوت مسموع (Think-Aloud Protocol)
- **فعل المحاضر:** يبتعد عن لوحة المفاتيح قليلاً، وينظر للطلاب، ويحلل المشكلة منطقياً دون كتابة سطر كود واحد.
- **ماذا يقول المحاضر؟**
  > *"أنا قبل ما أمد إيدي على الكيبورد، بسأل نفسي: هل الرصيد ينفع يبقى `double`؟ لا طبعاً، الفلوس في البنوك بنتعامل معاها بالـ Minor Units (قروش أو سنتات) عشان الـ Floating Point Precision. طب هل المعاملات متزامنة ولا ممكن تجيلي ورا بعض؟ لو متزامنة هحتاج Lock أو معالجة غير متزامنة. تعالوا نبدأ بأبسط حاجة ممكنة عشان نثبت الفكرة الأساسية."*

### الخطوة 3: الحل الأولي البسيط (The Naive / Working Implementation)
- **فعل المحاضر:** يكتب كوداً بسيطاً ومباشراً جداً، حتى لو كان فيه عيوب معمارية واضحة، ليثبت أن الكود يعمل في الحالة المثالية (The Happy Path).
- **كود حي يكتبه المحاضر:**
  ```dart
  class SimpleWallet {
    double balance; // خطأ متعمد: استخدام double بدلاً من int
    SimpleWallet(this.balance);

    bool withdraw(double amount) {
      if (amount <= balance) {
        balance -= amount;
        return true;
      }
      return false;
    }
  }
  ```

### الخطوة 4: كشف نقاط الضعف وتفجير الكود (Failure & Bottleneck Exposure)
- **فعل المحاضر:** يكتب كوداً يختبر الحل الأولي بحالات استثنائية (Edge Cases) حتى ينكسر البرنامج أمام الطلاب أو تظهر نتائج محاسبية خاطئة.
- **ماذا يقول المحاضر؟**
  > *"الكود شكله شغال وجميل صح؟ طب تعالوا نشغل السطرين دول ونشوف العجب:
  > ```dart
  > void main() {
  >   final wallet = SimpleWallet(0.3);
  >   wallet.withdraw(0.2);
  >   print('المتبقي في المحفظة: ${wallet.balance}');
  >   print('هل المتبقي بالضبط 0.1؟ ${wallet.balance == 0.1}');
  > }
  > ```
  > ندوس Run ونشوف في الـ Terminal:  
  > طلع المتبقي: `0.09999999999999998`! والمقارنة طلعت `false`!  
  > تخيلوا لو دي فلوس عملاء في البنك! شفتوا ليه المهندس الشاطر مبيفرحش بكود شغال وخلاص؟"*

### الخطوة 5: التحسين المعماري خطوة بخطوة (Refactoring Step-by-Step)
- **فعل المحاضر:** يعيد هيكلة الكود بهدوء، مستخدماً أفضل الممارسات التي درسوها: تحويل المبالغ لـ Minor Units، جعل المتغيرات غير قابلة للتعديل العشوائي (Encapsulation)، وتطبيق Sealed Class للنتائج.
- **ماذا يقول المحاضر؟**
  > *"تعالوا نصلح الكود مع بعض:  
  > 1. هنحول الـ `double balance` لـ `int minorUnits` (القروش).  
  > 2. هنمنع أي حد يعدل الرصيد من برة الكلاس مباشرة عبر `private field` و`getter`.  
  > 3. مش هنرجع مجرد `bool`، هنرجع `Result` نوعي يوضح سبب الفشل بدقة (هل الرصيد لا يكفي؟ ولا القيمة المدخلة سالبة؟)"*

### الخطوة 6: الاختبار الصارم (Automated Assert & Verification)
- **فعل المحاضر:** يكتب دوال تحقق سريعة باستخدام `assert` أو اختبارات مصغرة للتأكد من أن جميع الحالات تعمل بدقة متناهية.
- **كود حي يكتبه المحاضر:**
  ```dart
  void main() {
    final wallet = RobustWallet.fromEgp(100.0);
    final result1 = wallet.withdraw(Money.fromEgp(25.50));
    assert(result1 is WithdrawalSuccess, 'Should succeed');
    assert(wallet.balanceInEgp == 74.50, 'Balance must be exactly 74.50');
    
    final result2 = wallet.withdraw(Money.fromEgp(200.0));
    assert(result2 is InsufficientFundsFailure, 'Must detect overdraft');
    print('✅ جميع اختبارات الأمان المالي نجحت بنسبة 100%');
  }
  ```

### الخطوة 7: مناقشة البدائل والـ Trade-offs
- **فعل المحاضر:** يتوقف ويسأل الطلاب: ما تكلفة هذا الحل؟
- **النقاش المعماري:**
  > *"هل الحل ده كلفنا ذاكرة زيادة؟ لا، `int` بيشغل مساحة أصغر من `double` في الـ 64-bit Architecture.  
  > طب هل كلفنا تعقيد في الكود؟ شوية، بس كسبنا حماية تامة ضد أخطاء الحسابات.  
  > لو شغالين في لعبة ومش فارق معانا الفلوس ممكن الـ `double` يعدي، بس في FinTech ده غير مقبول نهائياً."*

## 3. بروتوكول التعامل مع الأخطاء غير المتوقعة (Unexpected Bug Protocol)

إذا حدث خطأ غير متوقع أثناء كتابتك للكود أمام الطلاب:
1. **لا ترتبك ولا تحاول إخفاء المشكلة:** هذا أعظم درس عملي يمكن أن تقدمه للطلاب!
2. **ابتسم وقل:** *"يا سلام! ظهر لنا Bug حقيقي على الهواء! تعالوا نشوف إزاي المهندس الكبير بيتعامل مع الـ Stack Trace"*.
3. **اقرأ رسالة الخطأ بصوت مسموع وركز على السطر ورقم العمود.**
4. **استخدم أسلوب الفرضية والاختبار (Hypothesis Testing):**
   - *"الـ Analyzer بيقول `Null check operator used on a null value` في السطر 42. تفتكروا مين المتغير اللي جواه null هنا؟ تعالوا نعمل `print` أو نحط Breakpoint ونفحص الـ State"*.
5. **أصلح المشكلة واشرح سبب حدوثها وكيفية تفاديها مستقبلاً.**

## 4. إعدادات بيئة العرض (Presenter IDE Rules)
- **Font Size:** حجم الخط 18pt كحد أدنى على الشاشة أو جهاز العرض (Projector).
- **Theme:** استخدام Dark Theme عالي التباين (High Contrast) أو Light Theme ناصع في القاعات المضيئة.
- **Keycasting:** تفعيل مؤشر اختصارات الكيبورد على الشاشة ليرى الطلاب الاختصارات البرمجية التي يستخدمها المحاضر.
- **Terminal Hygiene:** تنظيف الـ Terminal بأمر `clear` قبل تشغيل أي كود جديد لمنع تشتيت الانتباه.
- **Full Screen:** إغلاق النوافذ الجانبية غير الضرورية لتركيز عين الطالب على الكود الحي فقط.
